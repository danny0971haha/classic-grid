# Artifacts

`historical/classic-v0.2-checkpoint-e-results.non-authoritative.json` is the rejected Checkpoint E campaign file. Its `E-01`..`E-30` `result="PASS"` values were synthesized before the Node test process ran. It is kept only as a historical record and is **not** machine evidence.

Authoritative Checkpoint E evidence is the GitHub Actions artifact `classic-v0.2-checkpoint-e-results` generated by `tools/checkpoint-e-evidence.ts` with schema `classic-v0.2-checkpoint-e/3`:

```text
npm run evidence:checkpoint-e
npm run evidence:checkpoint-e:verify
```

The E generator runs two real suites:

- `checkpointSuite`: TAP from `test/experiment-v02-checkpoint-e.test.ts` (E-01..E-30)
- `projectSuite`: TAP from the same file list as `npm test`, plus the non-TAP `test/grid.test.ts` pre-check exit code

It does not copy the 30-case Checkpoint E TAP into `projectSuite`. It does not fill PASS from `CASE_IDS`. `fullSuite` is not a field in schema v3.

Checkpoint F evidence is generated by `tools/checkpoint-f-evidence.ts` with schema `classic-v0.2-checkpoint-f/2`:

```text
npm run test:checkpoint-f
npm run evidence:checkpoint-f
npm run evidence:checkpoint-f:verify
```

The F generator records separate identities:

- `sourceHeadSha` / `sourceHeadTreeSha`: PR head or push SHA from `EVIDENCE_SOURCE_HEAD_SHA`
- `testedCheckoutSha` / `testedCheckoutTreeSha`: the commit actually checked out (`git rev-parse HEAD`)
- `baseSha`: `EVIDENCE_BASE_SHA`

It does not copy `CHECKPOINT_E_*` names, does not store `requestedVerdict`, and does not treat `git rev-parse HEAD` as the PR source head. Independent `verify` must re-resolve identity from git and the workflow env.

Do not check in generated results JSON that claims the current commit SHA.

On `push`, `identity.sourceHeadSha` and `identity.testedCheckoutSha` may be the same commit. On `pull_request`, those SHAs must not be stored as one field.
